# 네이버 채널 음식 이미지 보정 기능 개발 이력

## 1. 문서의 목적과 범위

이 문서는 네이버 채널에서 음식 사진을 광고 문구와 함께 반환할 때, 원본 사진을 그대로 사용하던 초기 상태부터 음식 사진 보정 파이프라인을 설계·연결·검증한 과정을 시간순으로 기록한다.

모델 이름만 나열하는 문서가 아니라 다음 질문에 답하는 것을 목표로 한다.

- 어떤 사용자 문제를 해결하려 했는가
- 각 단계에서 무엇이 실패했고, 왜 설계를 바꾸었는가
- 현재 결과는 어떤 근거로 통과했는가
- 아직 일반화되었다고 말할 수 없는 부분은 무엇인가

이 문서의 최신 실험 근거는 Google Colab의 NVIDIA L4 GPU 환경에서 실행한 배경 교체 결과와 실행 보고서다. 한 장의 성공 사례는 기능 검증 근거이지만, 모든 음식 사진에 대한 성능 지표는 아니다.

## 2. 출발점: 네이버 채널의 이미지 처리 요구

초기 네이버 채널은 사용자가 올린 음식 사진을 광고 문구와 함께 그대로 반환했다. 원본 사진에는 식탁보, 주변 식기, 촬영 조명, 배경 잡동사니가 함께 남을 수 있으므로 음식점·카페 광고 이미지로 바로 쓰기 어려웠다.

따라서 다음 원칙을 세웠다.

1. 실제 메뉴인 음식과 용기는 가능한 한 원본 픽셀을 보존한다.
2. 생성 모델에는 원본 음식을 맡기지 않고, 음식이 없는 광고용 배경만 만들게 한다.
3. 음식 탐지·분할·합성·의미 검증 중 하나가 신뢰할 수 없으면 광고 이미지를 억지로 저장하지 않고 원본을 반환한다.
4. 네이버 API와 이미지 파이프라인은 같은 프로젝트 안에서 실행한다. 업로드 이미지를 별도 외부 서비스로 보내는 구조로 만들지 않는다.

현재 네이버 연동은 업로드 사진을 파이프라인 작업 파일로 저장하고, 성공한 합성 JPG를 광고 응답 이미지로 돌려준다. 실패하면 광고 문구 생성 자체를 실패시키지 않고 원본 사진과 실패 상태를 반환한다.

## 3. 전체 개발 흐름

```text
네이버 채널에서 음식 사진 업로드
  → 업종·음식 관련 JSON 수신
  → 음식·접시 후보 탐지
  → 음식/접시 구조 분할 및 접시 보존 알파 생성
  → 촬영 각도 분류
  → 업종·각도에 맞는 빈 배경 후보 생성
  → 빈 중앙 영역을 가진 배경 후보 선택
  → 원본 음식·접시 전경을 축소·배치
  → 접지 그림자·제한적 색 조화
  → 의미·기하·화질 검증
  → 성공: 합성 이미지 반환 / 실패: 원본 이미지 반환
```

## 4. 단계별 개발 이력과 의사결정

### 4.1 1차 목표: 음식의 위치를 안정적으로 찾기

초기에는 기본 YOLO11n COCO 모델로 음식과 용기를 찾으려 했다. 그러나 한식, 빵, 복합 음식, 무늬 접시 조합은 COCO 클래스에 충분히 포함되지 않아 음식 위치를 찾지 못하는 사례가 있었다.

이를 보완하기 위해 다음 두 계층을 만들었다.

| 순서 | 구성 | 역할 | 도입 이유 |
| --- | --- | --- | --- |
| 1차 | GroundingDINO Tiny | `plate`, `dish`, `bowl`, `food`, `meal`, `bread`, `cake`, `dessert` 텍스트로 후보 상자 탐지 | 고정 COCO 클래스에 없는 음식·접시 조합을 넓게 찾기 위해 사용 |
| 보완 | 음식 특화 YOLO11n | 프로젝트 음식 이미지로 학습한 `models/best.pt` 탐지 | GroundingDINO에서 찾지 못한 음식 위치를 보완하고, 기존 일반 YOLO11n과 비교하기 위해 사용 |
| 진단용 | 기본 COCO YOLO11n | `models/yolo11n.pt` | 모델 비교 및 장애 진단 때만 선택 가능 |

운영 모드에서는 중앙 사각형을 임의로 만들어 탐지 실패를 감추지 않는다. 음식·접시를 찾지 못하면 `food_detection_failed`로 종료한다. 중앙 사각형 대체는 연결 테스트 전용이다.

### 4.2 2차 목표: 접시가 사라지지 않도록 전경을 분리하기

음식 사진에서 가장 반복적으로 확인된 실패는 접시 외곽이 투명해지거나 일부가 잘리는 문제였다. 음식만 분리하려고 한 마스크가 접시 무늬, 반사광, 음식에 가려진 영역을 배경으로 오인했기 때문이다.

이를 해결하기 위해 전경을 하나의 마스크로 취급하지 않고 두 역할로 나누었다.

| 레이어 | 현재 방식 | 보존 대상 |
| --- | --- | --- |
| 음식 레이어 | GroundingDINO/YOLO 상자를 SAM 2.1 Small에 전달해 만든 음식 구조 마스크 | 실제로 보이는 음식 |
| 접시 레이어 | SAM 접시 마스크에 원형·타원형 윤곽 보완, 작은 외곽 결손 복구 | 접시 외곽과 음식 아래 접시 영역 |

접시 레이어는 원본 RGB 픽셀을 유지한다. 접시 알파의 불투명 커버리지와 내부 빈틈 비율을 별도로 검사하며, 기준을 만족하지 못하면 최종 광고 이미지를 저장하지 않는다.

후속 실험으로 `plate_full`, `food_visible` 두 클래스를 갖는 YOLO11-seg 접시 전용 분할 모델을 준비했다. AIHub 정제 이미지에서 후보를 추출하고 GroundingDINO와 SAM 2.1 Small으로 COCO 초안을 만든 뒤 사람이 경계·클래스·누락을 검수하는 흐름을 추가했으며, 후보 가중치 `models/yolo_seg_best.pt`도 존재한다. 다만 현재 `configs/pipeline.yaml`은 `models.plate_segmenter.enabled: false`이고 설정된 기본 경로 `models/yolo11n_plate_seg.pt`도 실제 후보 파일명과 다르므로 운영 기본에는 참여하지 않는다. 현재 기본은 SAM2·HQ-SAM과 기하학적 접시 보완이다.

### 4.3 BiRefNet HR 사용과 중단

초기에는 BiRefNet HR을 음식·접시 알파 매트 생성에 사용했다. 그러나 이 사례처럼 접시 전체를 보존해야 하는 사진에서는 접시 외곽에 불필요한 투명도나 결손이 생길 수 있었다.

그래서 현재 기본 설정에서는 BiRefNet HR을 끄기로 결정했다.

- `configs/pipeline.yaml`의 `models.matting.enabled`는 `false`다.
- 기본 모델 다운로드인 `scripts.download_models --all`은 BiRefNet을 받지 않는다.
- 현재 알파는 SAM의 음식 구조 마스크와 접시 보존 마스크만 사용한다.
- 이전 실행 호환을 위한 `--enable-matting` 옵션은 모델을 다시 켜지 않는 호환용 옵션이다.

이 결정은 BiRefNet이 항상 나쁘다는 의미가 아니다. 얇은 음식 경계를 부드럽게 만드는 별도 실험에는 다시 사용할 수 있다. 다만 현재 네이버 광고 이미지의 우선순위는 음식·접시 원본 보존이므로, 접시 외곽에 영향을 줄 수 있는 매팅 모델은 기본 경로에서 제외했다.

### 4.4 3차 목표: 촬영 각도와 배경 구도를 맞추기

탑뷰 음식 사진에 눈높이 카페 배경을 합성하면 음식이 공중에 뜨거나 테이블 위에 놓인 것처럼 보이지 않는 문제가 있었다.

그래서 촬영 각도를 배경 프롬프트, 전경 크기, 그림자까지 결정하는 입력으로 승격했다.

| 입력 우선순위 | 처리 |
| --- | --- |
| JSON의 `camera_angle_manual: true`와 `camera_angle_label` | 사용자가 명시한 `top` 또는 `45`를 우선 사용 |
| EfficientNet-B0 결과 | `models/efficientnet_best.pt`로 `top`, `45` 중 하나를 분류 |
| 낮은 분류 확률 | 최고 확률 클래스를 사용하되 보고서에 낮은 확률 상태를 기록 |

각도별로 빈 배경 프롬프트와 전경 배치 정책을 다르게 적용한다.

| 항목 | 탑뷰 | 45도 |
| --- | --- | --- |
| 배경 구도 | 수직 탑뷰의 빈 테이블 | 45도 시점의 테이블·실내 |
| 전경 위치 | 중앙 | 하단 중앙 |
| 전경 너비 기준 | 캔버스 너비의 약 40% | 캔버스 너비의 약 48% |
| 그림자 | 접시 테두리를 따라 짧고 약한 그림자 | 일반 접지 그림자 |

### 4.5 4차 목표: 배경을 한 장만 생성하지 않고 선택하기

생성 모델은 `no food`, `no plate`, `no people`, `no text` 같은 제약을 주어도 음식·컵·접시를 만들 수 있다. 따라서 배경 한 장을 생성해 바로 쓰는 방식은 중단했다.

현재 배경 선택은 다음 과정을 따른다.

1. 업종과 촬영 각도에 맞는 빈 배경 후보를 여러 장 생성한다.
2. 후보별로 중앙 배치 영역에 음식·접시·컵·식기가 있는지 점검한다.
3. 중앙 여백, 배경의 색온도, 객체 검출 여부를 점수화한다.
4. 배치 영역이 비어 있고 점수가 가장 높은 후보만 선택한다.

설정상 기본 후보 수는 3장이고, 유효 후보가 부족하면 최대 12회까지 재시도할 수 있다. 생성기는 Sana 1.6B를 기본으로 사용하며, FLUX.1 Schnell은 선택 가능한 대체 제공자다.

### 4.6 5차 목표: 자연스러운 합성과 안전한 결과 반환

합성 단계는 원본 전경을 배경 중앙에 단순 붙여넣기 하는 것이 아니다.

- 전경의 알파 영역을 기준으로 크기를 줄이고 안전 여백을 둔다.
- 광원 방향을 이용해 약한 접지 그림자를 만든다.
- 밝기·대비·채도·색상 이동은 설정된 범위 안에서만 조정한다.
- OpenCLIP은 전경 마스크 영역을 중립 배경에서 비교해 음식 의미가 지나치게 달라졌는지 검사한다.
- 배경 음식 탐지, 전경의 크기·위치 기하 검증, OpenCLIP, 화질 검증 중 하나라도 실패하면 합성 JPG를 저장하지 않는다.

네이버 API는 이 실패를 광고 문구 API 전체 오류로 처리하지 않는다. 원본 이미지를 반환하고, `food_detection_failed`, `semantic_validation_failed`, `geometry_validation_failed` 같은 상태와 보고서를 남긴다.

## 5. 네이버 채널 연결 구조

```text
네이버 블로그 채널 선택
  → 사용자가 음식 사진과 업종 JSON 입력
  → 광고 콘텐츠 API
  → food-image-cleanup-pipeline 실행
  → 성공한 합성 JPEG를 API 응답 image에 설정
  → 네이버 광고 문구와 함께 반환
```

연동 활성화는 API 환경 변수로 제어한다.

```env
BRANDMATE_NAVER_IMAGE_ENHANCEMENT_ENABLED=true
BRANDMATE_NAVER_IMAGE_CLEANUP_ROOT=food-image-cleanup-pipeline
BRANDMATE_NAVER_IMAGE_CLEANUP_PYTHON=C:\\경로\\파이프라인전용가상환경\\Scripts\\python.exe
BRANDMATE_NAVER_IMAGE_CLEANUP_TIMEOUT_SECONDS=600
```

동작 확인 시에는 API 응답에서 `vision_prompt.image_generation`이 `background_replacement_completed`인지, `image.model`이 `food-image-cleanup-pipeline`인지 확인한다.

## 6. 최신 Colab L4 실험 기록

### 6.1 실험 환경

| 항목 | 값 |
| --- | --- |
| 실행 환경 | Google Colab GPU 런타임 |
| GPU | NVIDIA L4 |
| 입력 이미지 | 1536 × 1536 음식 사진 1장 |
| 입력 품질 | 흐림·과도한 어두움·과도한 밝음·저대비·클리핑 모두 미검출 |
| 배경 생성 | 후보 4회 시도, 유효 후보 3장 |
| 알파 방식 | SAM 음식 구조 마스크 + 접시 보존 마스크, BiRefNet HR 미사용 |

이 실험의 실행 보고서는 `pipeline_version: 0.3.0`을 기록했다. 실행 시간, GPU 메모리 사용량, 비용은 이 보고서에 수집되지 않았으므로 본 문서는 해당 수치를 주장하지 않는다.

### 6.2 실제 단계별 결과

| 단계 | 결과 |
| --- | --- |
| GroundingDINO 탐지 | 음식 상자 7개, 용기 상자 1개 탐지 |
| 음식 특화 YOLO11n | 음식 상자 1개를 탐지했으나 GroundingDINO 보완 경로는 사용하지 않음 |
| SAM 2.1 Small | 음식 구조 마스크 7개, 접시 마스크 1개 생성 |
| 접시 보존 | 접시 알파 불투명 커버리지 1.0, 내부 빈틈 비율 0, 보존 검사 통과 |
| 촬영 각도 | `top` 분류, 확률 0.965236 |
| 배경 후보 선택 | 4번 후보 선택. 1번 후보는 중앙 배치 영역 객체 검출로 제외 |
| 전경 배치 | 중앙, 캔버스 너비 대비 0.39974, 배율 0.550673 |
| OpenCLIP 전경 검증 | 유사도 0.985584, 기준 0.8 통과 |
| 화질 검증 | 밝기 차이 12.95, 대비 차이 9.6122, 선명도 저하 비율 0.137246으로 통과 |
| 최종 상태 | `completed` |

최종 결과에서는 원본의 접시와 음식이 생성된 목재 테이블 배경 중앙에 축소 배치되었다. 이전처럼 접시가 크게 잘리거나 접시 중앙이 배경으로 뚫리는 문제는 이 사례에서 확인되지 않았다.

### 6.3 이 결과가 의미하는 것

이 결과는 다음 가설을 지지한다.

> 접시 외곽을 일반 매팅 모델에 맡기지 않고, SAM 구조 마스크와 별도 접시 보존 알파를 결합하면 원본 접시를 유지하면서 탑뷰 배경 합성이 가능하다.

근거는 접시 보존 검사 통과, 전경 의미 유사도 0.985584, 최종 화질 검증 통과, 그리고 실제 출력 이미지에서 접시와 음식이 유지된 점이다.

다만 이 결과 하나만으로 모든 음식·접시·조명·각도에 대해 자연스럽다고 결론 내릴 수는 없다.

## 7. 현재 구현된 파일과 역할

| 위치 | 역할 |
| --- | --- |

## 9. 현재 한계

1. 최신 성공 결과는 한 장의 탑뷰 음식 사진 기준이다. 다양한 접시 재질, 투명 용기, 어두운 음식, 45도 사진에 대한 정량 평가는 더 필요하다.
2. 생성 배경이 가장자리에 컵·식물·식기를 만들 수 있다. 중앙 배치 영역은 검사하지만 장면 전체가 완전히 비어 있다는 보장은 아니다.
3. 현재는 원본 음식과 접시의 픽셀을 보존하는 정책이라, 원본과 생성 배경의 조명 색온도가 크게 다르면 완벽한 광원 일치는 어렵다. 직접 재조명은 음식 외형을 바꿀 위험이 있어 기본 경로에서 사용하지 않는다.
4. 접시 전용 YOLO11-seg 후보 가중치는 있지만 기본 설정에서 비활성화되어 있다. 타원·사각형 계열·비정형 용기 분기는 추가됐지만, 투명 유리 그릇이나 강하게 가려진 접시는 림 관찰 신뢰도가 낮아 보정이 생략될 수 있다.
5. Colab L4에서 기능은 실험했지만, 모델별 지연 시간·최대 VRAM·실행 비용을 구조적으로 기록하지 않았다.
6. 음식 지지 구조 복구는 오탐을 줄이기 위해 기하학만으로 채택하지 않는다. 이 때문에 실제 꼬치도 `food_support_mask`에 포함되지 않을 수 있다.

마지막 문서 갱신 이후 코드에는 특정 초록색 원형 접시에 맞춘 림 복원을 다양한 용기로 확장하기 위한 변경이 추가되었다.

### 12.1 용기 형태별 마스크 정리

`PlateMaskService`는 용기를 `ellipse`, `quadrilateral`, `irregular`로 판정한다. 타원과 사각형 계열은 형태 신뢰도가 충분할 때만 완성하고, 저신뢰·비정형 결과는 원본 연결 영역을 유지한다. 목적은 흰 접시, 유색 접시, 그릇과 트레이에 임의의 초록색 타원을 그리지 않는 것이다.

### 12.2 음식·접시 품질 검사 분리

음식은 여러 조각으로 나뉠 수 있지만 접시는 큰 연결 영역이어야 하므로 두 마스크를 별도 규칙으로 검사한다. 결과는 `step_2c_mask_quality`에 기록한다. `generated_plate`에서 음식 마스크가 실패하면 원본 용기가 섞일 위험 때문에 합성을 중단하고, preserve 모드에서는 저신뢰 림 보정을 차단한다.

### 12.3 꼬치형 음식 지지 구조

GroundingDINO 프롬프트에 `wooden skewer`, `food skewer`, `chopstick`을 추가했다. Canny와 HoughLinesP로 가는 선 후보를 찾되 접시 경계 통과, 음식 연결, 방향·길이·면적, SAM/HQ-SAM 후보 증거를 모두 확인한다. `allow_geometry_only: false`이므로 수저나 테이블 선처럼 모양만 비슷한 구조는 복구하지 않는다.

음식 지지 구조를 용기 블러와 림 보정 뒤 최상단 RGB 레이어로 다시 그리는 실험도 진행했지만 사용자 요청으로 롤백했다. 현재 코드에는 `step_5e_food_support_layer`가 없고 `step_2d_food_support_recovery`에서 만든 보호 마스크만 사용한다.

### 12.4 원본 RGB 기반 적응형 림 관찰

고정된 초록색 HSV 범위 대신 원본 용기 외곽에서 색 군집, 경계 기울기와 윤곽 적합도를 계산한다. 관찰 신뢰도가 `minimum_confidence: 0.53`보다 낮거나 음식·접시 품질 검사가 실패하면 합성 림 브리지와 접시 알파 확장을 적용하지 않는다. 이 정책은 잘못된 선 생성을 줄이지만, 확신이 부족한 실제 결손도 그대로 남길 수 있다.

중간 실행에서는 음식·접시 품질 검사는 통과했지만 림 관찰 신뢰도 `0.480164`가 기준보다 낮고 음식 지지 구조도 `kept_components: 0`, `recovered_pixels: 0`으로 기록된 사례가 있었다. 이 값은 안전 게이트 조정 과정의 이전 실패 사례이며 최신 결과가 아니다.

이후 Colab 최종 결과 `example_background_replaced.jpg`를 시각 검증한 결과, 접시 상단의 초록색 림이 꼬치 교차 구간을 포함해 연속적으로 복원됐고 여러 꼬치 끝도 접시 바깥까지 보존됐다. 최신 시각 결과는 림 복원과 꼬치 보존이 적용된 성공 사례다. 대응 JSON 리포트가 함께 제공되지 않았으므로 정확한 브리지·복구 픽셀 수는 기록하지 않는다.

### 12.5 Colab 호환성과 회귀 도구

OpenCV HoughLinesP 결과가 환경에 따라 `(N, 1, 4)` 또는 `(N, 4)`로 반환되는 차이를 `reshape(-1, 4)` 정규화로 처리했다. 이 수정은 검출 임계값이나 모델 출력을 바꾸지 않고 `numpy.int32 object is not iterable` 실행 오류만 방지한다.

`scripts/build_container_generalization_regression.py`와 `scripts/evaluate_container_generalization_regression.py`는 접시·그릇·트레이·컵 조건의 고정 회귀 세트와 실행 보고서 집계를 위한 도구다. 도구가 추가된 것과 전체 50장 E2E 평가가 완료된 것은 다르므로, 집계 보고서를 만들기 전에는 일반화 완료로 판단하지 않는다.
